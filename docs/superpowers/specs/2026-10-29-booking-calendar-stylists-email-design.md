# Booking approval, calendar, editable stylists and confirmation email

Date: 2026-10-29 · Branch: `feature/server-backend` · Status: awaiting owner review

## Goal

The owner handles booking requests like this:

1. A customer submits the booking form (now including an email address and a stylist dropdown).
2. The request appears in the admin panel as **new** (the existing phone alert still fires).
3. The owner phones the customer, then presses **Accept**.
4. The booking shows on the admin calendar and a confirmation email goes to the customer.

Declining cancels the request and frees the slot. No email is sent on decline.

## Decisions already made with the owner

- Emails are sent through the owner's own mailbox over SMTP (e.g. Gmail with an app password), using only Node built-ins (no new npm package).
- The stylist dropdown keeps one fixed first option, "First available stylist". Real stylists come from the server and are editable in the admin panel.
- The email address is required on the booking form.
- Declined and cancelled bookings are hidden in the calendar (still visible in the list view).
- Bulgarian-language confirmation email, sent once, when a booking becomes **confirmed**.

## Data model

- `store.catalog.stylists`: `{ id, name, role, experience }[]` (max 30). Ids are generated by the server (`st-` + random hex) for new entries.
- Migration: when an existing `store.json` has no `catalog.stylists`, copy `seed.stylists` without the virtual `any` entry. Reset-to-defaults restores the seed list. Catalog export/import includes stylists.
- `any` is a virtual option handled in code, never stored, never editable.
- Booking gains `email` (string, may be empty on old records), `emailSentAt?` (ISO string), `emailError?` (short text, no secrets).
- A booking keeps `stylistName` as written at request time, so removing a stylist never breaks old records.

## Server API

| Endpoint | Change |
|---|---|
| `GET /api/catalog` | also returns `stylists` |
| `POST /api/bookings` | requires `email` (basic format check, ≤120 chars); stylists validated against the stored list instead of the seed |
| `PUT /api/admin/stylists` `{ items }` | replaces the list; validates name (required, ≤100), role and experience (≤150), 0–30 items; assigns ids to new items; returns the catalog |
| `PATCH /api/admin/bookings/:id` | when status changes to `confirmed` (from any other status) the server sends the email and returns `{ booking, email }` where `email` is `sent`, `failed`, `disabled` or `no_address`. The status change is saved even if sending fails |
| `POST /api/admin/bookings/:id/email` | resend for a confirmed booking; same result shape |

The existing rule stays: a pending or confirmed booking with a named stylist blocks the same date and time for that stylist; cancelled frees it.

## Email (server/mailer.mjs)

- Config in `.env`: `SMTP_HOST`, `SMTP_PORT` (587 = STARTTLS, 465 = TLS from the start), `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`, plus `SALON_ADDRESS` and `SALON_PHONE` for the email body (defaults taken from the site's contact details).
- Minimal SMTP client over `node:net` / `node:tls`: EHLO, STARTTLS when needed, AUTH PLAIN/LOGIN, MAIL FROM, RCPT TO, DATA with dot-stuffing, QUIT. UTF-8 plain text, base64 body, RFC 2047 subject.
- Header-injection guard: CR/LF stripped from addresses, names and subject.
- 10-second overall timeout. The password is never logged or returned to the browser.
- Without SMTP settings the mailer reports `disabled`, and the admin panel says emails are switched off.
- Body lists date, time, service, stylist, salon address and phone.

## Front end

- `types.ts`: `Stylist` list on `Catalog`, `email` and email-status fields on `BookingRecord`.
- `Booking.tsx`: stylist cards become a `<select>` (first option "First available stylist"), new required email field, stylists read from the loaded catalog.
- `AdminPanel.tsx`:
  - New **Team** tab to add, edit and remove stylists. Removing one with upcoming bookings asks for confirmation.
  - Bookings tab gets a List / Calendar toggle. Pending requests get **Accept** and **Decline** buttons (Decline asks to confirm). Accepted bookings get Done / No-show / Cancel.
  - Each booking shows the email result (sent, failed with a **Resend** button, no address, or emails switched off).
- `BookingCalendar.tsx` (new): month grid, Monday first, previous / next / Today, chips per day (amber = pending, green = accepted), days with pending requests highlighted, click a day for the detail list sorted by time, tap-to-call phone, warning when two accepted bookings share the same stylist, date and time.
- Fix: the invisible-text buttons. They use a class `gold-btn` that is not defined (only `gold-btn-gradient` is). Replace with the defined class.
- Dates are the salon's local `YYYY-MM-DD` strings and are never converted between time zones.

## Error handling

- Mail failure never blocks Accept; it is stored on the booking and shown with Resend.
- Invalid email, unknown stylist and over-long fields are rejected with the existing Bulgarian error messages.
- Old bookings without an email can still be accepted and show "no email on file".
- Concurrent edits go through the existing store transaction.

## Testing

- Server tests (the existing `node --test` suite) extended with an in-process fake SMTP server: email content and encoding, STARTTLS and plain paths, failure and timeout, header-injection attempt, disabled mode, resend.
- Server tests for stylist validation and the migration, booking with and without email, Accept sending exactly once, Decline sending nothing, slot clash behaviour.
- Browser check: build the real site with the local esbuild and Tailwind, run the real server, then exercise submit, accept, decline, calendar and the Team tab and capture screenshots.

## Out of scope

Emails on decline, SMS, reminders, per-stylist working hours, showing free slots to customers, customer self-cancel, drag-and-drop calendar.

## Known limits

- Some home internet providers block outgoing mail ports 587 and 465.
- Gmail requires two-step verification and an app password.
- Real delivery cannot be tested from the build workspace; it is tested against the fake server only.
